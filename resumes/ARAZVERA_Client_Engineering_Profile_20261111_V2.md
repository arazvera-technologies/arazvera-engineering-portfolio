### Engineering that addresses real failure modes

We build **bounded, testable software components** for teams that need an API they can trust, an integration that survives retries, or a workflow with traceable decisions. Our approach starts from the failure case and written acceptance criteria—not a generic AI demonstration.

**Typical problems we can scope:**
- **Unreliable webhooks or background jobs:** signed ingress, idempotent processing, retries, dead-letter review, restart recovery.
- **Data integrity and access boundaries:** transactional imports, tenant-aware authorization, PostgreSQL RLS/role tests, safe rollback.
- **Unsafe changes and weak recovery evidence:** deployment HOLD/rollback rehearsal, observability checks, worker and database restore exercises.
- **Uncontrolled agent-tool access:** deny-by-default policies, human approval, budgets, allowlisted actions, evidence logs.
- **Inconsistent supplier or governance records:** deterministic data checks, exception reports, manual review and approved export.

### What a customer receives under an agreed scope

1. **Written technical design** — inputs, data boundaries, exclusions, risks and acceptance conditions.
2. **Implementation or adaptation** — a narrowly defined module, API, integration, validator or test harness.
3. **Reproducible evidence** — automated tests, negative-path scenarios and a results record.
4. **Operational handover** — configuration guide, deployment/staging checklist, logs or runbook as applicable.
5. **Explicit remaining work** — environment-specific tasks, licensing, threat review and acceptance decisions.

The exact deliverables, source ownership, timelines and support are set in the contract. Nothing implies unrestricted source transfer.
