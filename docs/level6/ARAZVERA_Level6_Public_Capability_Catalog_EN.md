## L6-BESS-001 | Battery Supplier Evidence Preflight

**Buyer problem:** supplier, pack, model and evidence records can disagree before they reach a customer's existing battery data or Digital Product Passport workflow.

**What the tool does:** checks four synthetic CSV tables, duplicate IDs, broken references, mismatched models and evidence suppliers, basic numeric validity and conflicting change events. The **v0.2 local candidate** also accepts strict JSON field-mapped records and can retrieve a JSON payload from a mock HTTP server bound to `127.0.0.1` on the operator's PC.

**Technical evidence:** 79 locally passing automated Python tests, source ZIP extraction/standalone retest, clean and deliberately defective synthetic fixtures, deterministic report JSON/CSV and SHA256 receipts. Safe non-source preview is available for evaluation.

**Potential adaptation:** map a buyer's authorized supplier export to the test schema; validate import and reconciliation in their approved sandbox; add evidence reporting requested in an agreed written scope.

**Limits:** no full EU Battery Passport, no official 71-field semantic applicability test, no DPP Registry integration, no ERP credentials, no production deployment and no regulatory certification. The v0.2 code passed four hosted BESS CI jobs on Ubuntu/Windows Python 3.11/3.12; the four-job CRA/DORA specialty matrix also passed. No customer industrial API or production acceptance was tested.

**Commercial route:** discuss a written, paid synthetic-first import/reconciliation QA pilot. Nonexclusive source licensing may be considered only after verified IP rights and lawful contracting.

## L6-CRA-001 | Cyber Resilience Act Incident Readiness

**Buyer problem:** incident evidence and internal reporting timelines may be incomplete, contradictory or difficult to review consistently.

**What the tool does:** local synthetic incident timeline checks, duplicate JSON object-key defense, missing evidence alerts, reporting-sequence findings and human-review prompts.

**Technical evidence:** version 0.2.0, 34 automated Python tests passed locally; deterministic clean/error examples and independently checked source and non-source preview packages.

**Potential adaptation:** align synthetic exercise fields to a manufacturer's documented PSIRT process, produce a technical rehearsal report and add scenario tests under a specialist-reviewed brief.

**Limits:** no connection/submission to ENISA SRP, no legal classification of reportable events, no official conformity assessment or real incident response representation.

**Commercial route:** a bounded tabletop/test-harness pilot with documented review and written acceptance, not an offer of legal compliance certification.

## L6-DORA-001 | ICT Provider Data and Evidence Triage

**Buyer problem:** duplicative or mismatched ICT provider/contract/feedback records can make review and reconciliation costly.

**What the tool does:** checks three synthetic CSV data sets, missing references, duplicates, LEI check digits and selected provider-identity anomalies, returning deterministic review findings.

**Technical evidence:** version 0.2.0, 33 automated Python tests passed locally; verified preview files contain no executable source.

**Potential adaptation:** a bounded prefiling data-quality test against buyer-approved exports and an explicit, reviewed field map.

**Limits:** no official EBA RoI validation rules, full DORA XBRL-CSV taxonomy implementation, accepted EBA filings or legal assurance.

**Commercial route:** written-scope paid data QA pilot; more extensive regulatory development requires an external subject-matter expert and documented buyer demand.
